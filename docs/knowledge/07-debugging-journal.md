# Debugging Journal

## Issue 1: Phone cannot see VM console
- **Symptom**: Phone shows 'This site can't be reached' at 192.168.1.85:7681
- **Root cause**: VM is on Hyper-V internal bridge (192.168.1.x), phone is on Wi-Fi (192.168.31.x). Different subnets, no route.
- **Fix**: Windows netsh portproxy + frontend URL rewrite to use window.location.hostname
- **Files changed**: ConsoleModal.tsx (line 45), Windows firewall rules
- **Lesson**: Never hardcode internal VM IPs in frontend code

## Issue 2: ActionBar.tsx syntax errors (recurring)
- **Symptom**: `npm run build` fails with TS2657/TS1005 errors

- **Fix**: Rewrote entire ActionBar.tsx cleanly via base64 encoded content

## Issue 5: PowerShell string escaping breaks node -e commands
- **Symptom**: node -e with template literals fails due to backtick interpretation
- **Root cause**: PowerShell uses backtick as escape character, conflicts with JS template literals

## Issue 6: "VM is running, but no IP was reported" banner never clears after a recovered provisioning failure
- **Symptom**: User created a Windows 11 VM that failed first time with `MAX 4 vcpus allowed per VM on this node`. After fixing the vcpu limit in Proxmox and getting the VM running, the frontend permanently showed the "no IP" banner. Restart did nothing. Previous Windows VMs (provisioned cleanly first try) worked fine.
- **Root cause**: `vm_ip` was only written in one place — the initial Celery provisioning task at `backend/app/tasks/vm_tasks.py:136` (`proxmox.get_vm_ip_from_agent`). When the task hit `ProxmoxAPIError` at `qm start`, it jumped to the exception handler and wrote `status=failed` with `vm_ip=NULL`, never reaching the IP poll. The Start/Restart action endpoint at `backend/app/routes/vm_routes.py:408` only called `proxmox.start_vm` and never re-polled, so `vm_ip` stayed NULL forever. Frontend banner at `frontend/src/pages/VMDetailPage.tsx:86` is keyed off `vm.status === "done" && !vm.vm_ip`, so it was stuck on. The banner text even told users to "restart the VM" — which is exactly what didn't help, because Restart didn't re-poll either.
- **Fix (part 1)**: Added `_refresh_vm_ip_async()` helper in `backend/app/routes/vm_routes.py` and a FastAPI `BackgroundTasks` parameter on the PATCH endpoint. After a successful Start or Restart, if `job.vm_ip` is NULL the helper is scheduled to run after the response returns. It polls the QEMU guest agent for up to 180s and writes the IP back via `database.update_vm_job(vm_ip=...)`. Uses `COALESCE` so other fields are preserved.
- **Fix (part 2)**: The PATCH-only path turned out to be too narrow — VM 109's guest agent was asleep during Windows Update, the 180s poll timed out, and the user had no way to recover without rebooting again. Added an **opportunistic IP self-heal** to the GET `/vms/{job_id}` endpoint: if `live_status == "running"` and `vm_ip` is NULL, do a single 10s agent poll and write the result back to the DB. Cheap (skipped entirely when IP already set), self-healing on every page refresh, no reboot needed.
- **Why background on PATCH but inline on GET**: The PATCH poll has to allow up to 3 minutes (cold boot scenarios). GET runs on every page load and dashboard tick, so it must stay fast — 10s is a generous ceiling for an alive agent which responds in <1s.
- **One-off DB patch for VM 109**: While Windows Update was running, the agent never reported. After update finished and the IP appeared in Proxmox (192.168.1.2), the DB row was patched directly: `UPDATE vm_jobs SET vm_ip = '192.168.1.2' WHERE id = 53`. Going forward the GET self-heal handles this class of case automatically.

- **Bonus bug #1 — credentials never written**: When VM 109 was patched with an IP and the user clicked Desktop, it failed with "VM is missing IP or credentials". Same root cause: the Celery `except` handler bailed out before `vm_username` / `vm_password` were written at `vm_tasks.py:152-160`. Patched the row directly (`UPDATE vm_jobs SET vm_username = ..., vm_password = ...`) using the values from `VM_WINDOWS_USERNAME` / `VM_WINDOWS_PASSWORD` env vars, then added a credential self-heal block to the GET endpoint alongside the IP one. Credentials come from env vars (deterministic, no network), so backfill is basically free — `os_choice` on the job tells us which credentials to apply.

- **Bonus bug #2 — `desktop-session` route called wrong function name**: After patching credentials, the Desktop button returned `500 Internal Server Error`. Backend traceback showed `AttributeError: module 'app.services.guacamole_client' has no attribute 'create_windows_desktop_session'. Did you mean: 'create_desktop_session'?`. A rename refactor had updated the client module but not the call site in `backend/app/routes/desktop_routes.py:83`. One-line fix: `guacamole_client.create_windows_desktop_session(...)` → `guacamole_client.create_desktop_session(...)`. **This bug had been in main for some time**, but nobody had hit it because no Windows VM had ever reached this code path before — they all died at the missing-IP banner first. Fixing bug #6 / bonus #1 exposed it.

- **Lesson**: When a single code path is the *only* writer for a field, any error in that path leaves the field unrecoverable. Backfill hooks belong on the **read path** too, not just on the action endpoints — because the read path runs continuously and self-corrects without user intervention. Also: bugs hide other bugs. A broken happy-path can mask any number of downstream bugs because nothing ever reaches them. Every time you unblock a stuck flow, expect to discover the next thing that was silently broken.

## Issue 7: All logins fail with "Invalid username or password" after adding RAG deps
- **Symptom**: Immediately after adding the RAG dependencies and rebuilding, every login (with correct credentials) returned "Invalid username or password". Backend logs showed a traceback ending in `ValueError: password cannot be longer than 72 bytes` from inside `passlib/handlers/bcrypt.py` → `detect_wrap_bug` → `_bcrypt.hashpw`.
- **Root cause**: Two-step. (1) `requirements.txt` pinned `bcrypt==3.2.0`, but `chromadb` requires `bcrypt>=4.0.1` → pip `ResolutionImpossible`. (2) Unpinning to `bcrypt>=4.0.1` let pip install **bcrypt 5.0.0**, which (like all bcrypt ≥4.1) **raises** on >72-byte passwords instead of silently truncating. `passlib 1.7.4`'s startup `detect_wrap_bug` probe deliberately hashes a long test password and does NOT catch that `ValueError`, so its bcrypt backend fails to initialise → **every** `verify()` throws → all logins 401. passlib 1.7.4 is the latest release and won't be fixed.
- **Fix**: Pin `bcrypt==4.0.1` in `backend/requirements.txt` — the last release before the 4.1 breaking change, and it still satisfies chromadb's `>=4.0.1`. Hot-patched the running containers first (`docker compose exec -u root backend pip install bcrypt==4.0.1`; the venv is root-owned so `-u root` is required), then baked the pin into the image via rebuild.
- **Files changed**: `backend/requirements.txt` (line ~22, with a warning comment not to bump).
- **Lesson**: passlib 1.7.4 is incompatible with bcrypt ≥4.1 — pin `bcrypt==4.0.1` whenever both passlib and a modern bcrypt consumer (like chromadb) are in the same env. A "harmless dependency unpin" silently broke auth for everyone. Also: a pinned transitive dep that another package needs newer = `ResolutionImpossible`; resolve by finding the one version that satisfies *both* constraints, not by removing the pin entirely.

## Issue 8: RAG "Vector store unavailable" — chromadb can't open its SQLite file
- **Symptom**: Admin → Knowledge Base showed "Vector store unavailable". Backend logs: `chromadb.errors.InternalError: error returned from database: (code: 14) unable to open database file` at `chromadb.PersistentClient(path=CHROMA_PATH)`.
- **Root cause**: The container runs as non-root `appuser` (uid 1000), but Docker creates **named-volume mountpoints owned by root**. The `chroma_data` and `hf_cache` volumes mounted at `/home/appuser/app/data/chroma` and `/home/appuser/.cache/huggingface` were `root:root`, so appuser couldn't create ChromaDB's SQLite file (SQLite error 14). Compounded by `WORKDIR /home/appuser/app` creating that dir as root even though the user is appuser.
- **Fix (runtime, durable for existing volume)**: `docker compose exec -u root backend sh -c "chown -R appuser:appuser /home/appuser/app/data /home/appuser/.cache"` then `docker compose restart backend`. Ownership persists in the volume.
- **Fix (permanent, fresh installs)**: In `backend/Dockerfile`, BEFORE the `USER appuser` switch (so it runs as root), `mkdir -p` the two dirs and `chown -R appuser:appuser` them. Docker seeds an empty named volume with the mountpoint's ownership on first mount, so appuser owns them from the start. (First attempt failed: the `mkdir` was placed *after* `USER appuser`, and appuser can't create a subdir under the root-owned `WORKDIR` — must be done as root pre-switch.)
- **Also improved**: `rag_service._ensure_ready()` now guards on `_collection is not None` instead of an `_initialized` flag, so a transient init failure (e.g. model still downloading) **retries** on the next call / "Refresh" instead of staying stuck until a process restart.
- **Windows gotcha**: `docker compose exec` Unix paths got mangled by Git Bash MSYS path conversion (`/home/...` → `C:/Program Files/Git/home/...`). Wrap the command in `sh -c "..."` so the paths are interpreted inside the container, not by the host shell.
- **Lesson**: Non-root containers + Docker named volumes = root-owned mountpoints by default. Pre-create and chown the mount paths in the Dockerfile (as root, before the USER switch) so empty volumes inherit the right ownership. See [[10-rag-knowledge-base]] and [[02-docker-infrastructure]].

## Issue 9: RAG agent says "couldn't find anything" although the document is indexed
- **Symptom**: Admin -> Knowledge Base showed the PDF as indexed (38 chunks, vector store online), but asking the ChatOps agent a covered question returned "I couldn't find anything about that in the knowledge base." Backend logs: `chromadb.errors.InternalError: Error executing plan: Internal error: Error creating hnsw segment reader: Nothing found on disk`.
- **Root cause**: The verification ingest was run in a SEPARATE one-off Python process while the backend (uvicorn) was already running. ChromaDB's `PersistentClient` caches its HNSW vector index in memory and is NOT designed for two processes sharing one path. The external process wrote the index to disk; the running backend's cached client never reloaded it, so vector search failed. `count()` still worked (it reads the DB directly), which is why stats showed 38 chunks while search found nothing - a telling split.
- **Why it does not happen in normal use**: Admin uploads go THROUGH the backend process (POST /admin/knowledge/upload), so the same process writes the index and reads it. The split only occurs when something writes the store out-of-band.
- **Immediate fix**: `docker compose restart backend` - a fresh client reads the complete on-disk index.
- **Hardening (so it self-heals)**: `rag_service.search()` now (1) short-circuits to [] when the collection count is 0 (querying an empty index also throws this error); (2) on any query failure, calls `_reset()` to drop the cached client/collection and retries once with a fresh client; (3) raises `RagError` only if it still fails. The agent catches `RagError` and reports a real failure ("I hit a problem searching...") instead of the misleading "couldn't find anything" (which now means genuinely zero matches). See [[10-rag-knowledge-base]].
- **Lesson**: Treat "no results" and "the query crashed" as different outcomes - collapsing them hides bugs and misinforms users. And single-writer assumptions in embedded stores (ChromaDB, SQLite) break the moment a second process touches the same files; either funnel all writes through one process or reset/reopen the client to pick up external changes.

## Issue 10: Concurrent clones of the same source VMID raced on a Proxmox file lock — found in live E2E
- **Symptom**: A 2-student bulk distribution of a template consistently produced a `partial` batch — one clone succeeded, the other failed with `qmclone: can't lock file '/var/lock/qemu-server/lock-<source_vmid>.conf' - got timeout`. Reproduced cleanly: with `worker_concurrency=2` in Celery, both ForkPoolWorkers picked up clone tasks for the same source at the same moment.
- **Root cause**: Proxmox itself takes an exclusive OS-level flock on `/var/lock/qemu-server/lock-<source_vmid>.conf` for the duration of every clone read. Two concurrent `clone_vm` API calls against the same `template_vmid` collide on that lock; the loser times out. This is hypervisor-level behaviour, not a bug in our stack — but our distribute endpoint exposes it on every multi-student bulk that hits the same template.
- **Why it wasn't caught earlier**: Compile checks and `tsc` pass; the per-source race only emerges under concurrent traffic against real Proxmox. Single-clone tests never hit it.
- **Fix**: In `backend/app/tasks/clone_tasks.py`, added `_source_clone_lock(source_vmid)` — a per-source Redis lock keyed by `privatecloud:lock:clone_source:<vmid>`. Wraps the `clone_vm` + `wait_for_task` block so workers cloning the same source queue politely. Lock auto-expires after 600s so a crashed worker can't deadlock the system. Cross-source clones (different templates) still run in parallel — verified by Test 33 in `docs/recent-work/09`.
- **Verification**: After the fix, `batch.status = completed` (was `partial`). Concurrent distributions across two DIFFERENT templates both completed end-to-end; same-source clones serialised (verified by per-clone timing in the Celery log).
- **Lesson**: When the underlying service (Proxmox here, but applies to any hypervisor / DB taking flocks) holds a per-resource lock during slow operations, your client-side concurrency cap doesn't help — you need a client-side per-resource lock that mirrors the server-side lock semantics. The lock key has to be the upstream resource, not your own job ID.

## Issue 11: Two Celery workers concurrently running `init_db()` deadlocked on `ALTER TABLE` — found in live E2E
- **Symptom**: On the first clone task after a fresh worker pool, one ForkPoolWorker crashed before processing its task: `psycopg2.errors.DeadlockDetected: deadlock detected ... Process X waits for AccessExclusiveLock on relation ... blocked by process Y; Process Y waits for AccessExclusiveLock ... blocked by process X.` The crashed worker's clone job was left stuck at `queued` and the batch never rolled up because the task died before the `finally` block ran.
- **Root cause**: `db/database.py:init_db()` runs a schema setup block that includes `ALTER TABLE audit_logs DROP CONSTRAINT IF EXISTS ... ADD CONSTRAINT ...`. Each Celery `ForkPoolWorker` is a separate process with its own connection pool, so each runs `init_db()` once on first task. With `worker_concurrency=2`, both workers process their first task simultaneously, both call `init_db()`, both grab AccessExclusiveLocks on the same table and rows — and Postgres detects the deadlock and aborts one.
- **Why it wasn't caught earlier**: Single-task runs only fire one worker, so only one process ever touches `init_db()`. The race only surfaces when the worker pool warms up under simultaneous traffic — exactly what happens on the FIRST request after a restart.
- **Fix**: In `db/database.py`, the very first statement inside the schema-setup transaction is `SELECT pg_advisory_xact_lock(7501231)`. Transaction-scoped advisory locks are exclusive across sessions; only one connection runs the schema block at a time and the others queue until it commits. Auto-releases on `COMMIT`. Zero overhead in steady state (lock held for <100 ms once the schema is already current).
- **Verification**: After the fix, parallel worker startups complete without deadlock. The full E2E (`docs/recent-work/09`) ran 9 successful clones across multiple batches with no DeadlockDetected events in the Celery log.
- **Lesson**: Postgres advisory locks (`pg_advisory_lock`, `pg_advisory_xact_lock`) are the right tool for "serialise this critical section across sessions without table-level locks". They're cheap, transaction-aware, and let you keep idempotent schema-setup code without paying the deadlock tax under concurrent startup. The bigger lesson is the same as Issue 10: code that's race-free under single-threaded invocation isn't necessarily race-free when your runtime fan-out fires it concurrently.

## Issue 12: "Publish template" created clones, not real Proxmox templates — reported from live Proxmox UI
- **Symptom**: The admin compared the app's Templates page (5 cards) against the Proxmox node view and saw only ordinary running VMs — none of the published templates appeared as Proxmox *templates* (the way the global golden images `9000 ubuntu-2404-golden` / `9001 windows-template` do). Templates were also not available anywhere on the user-facing Deploy page.
- **Root cause (design, not a crash)**: The original Sprint-5 implementation treated a "template" as a `vm_templates` row that merely *pointed at* the admin's still-running source VM (`source_vmid`). Distribution full-cloned that running VM. Only the linked path ever called `convert_to_template`, and that froze the *source* itself. So in full mode (the default) nothing was ever converted to a Proxmox template — exactly what the admin observed.
- **Fix**: Reworked publish to build a **dedicated, frozen Proxmox template** like 9000/9001 but private/scoped. Added `vm_templates.template_vmid`; publish now allocates a VMID, creates the row in `building`, and dispatches `clone.build_template` (full-clone source → `template_vmid`, then `convert_to_template`). The source VM is left running/usable. Distribute and the new admin-only deploy both clone from `template_vmid`. Added an admin-only "Templates" category to the Deploy page (`TemplateSelector` + `POST /templates/{id}/deploy` → `clone.deploy_for_user`). Statuses `building`/`failed` added; `get_reserved_vmids()` now also reserves building templates' VMIDs. See [[11-clone-templates]].
- **Decisions taken with the user**: (1) build a dedicated template by clone-then-freeze rather than freezing the source (keeps the admin's VM usable); (2) keep templates private/scoped, not global like 9000/9001; (3) Deploy-from-template is **admin-only**.
- **Lesson**: A "template" feature has to actually produce the platform's native template object, or it's just a clone with extra bookkeeping. When a primitive already exists (`convert_to_template`), wire the feature to it instead of approximating. Also: the linked-vs-full distinction belongs at *clone* time (off a real template), not at *publish* time — conflating them is what made full-mode templates fake.

## Issue 13: Windows template clones marked failed though Proxmox finished them — clone-wait timeouts too short
- **Symptom**: Publishing a Windows-11 template succeeded (template vmid 135 frozen, status=published), but distributing it to a class produced `failed` clone_jobs: `Task ...qmclone:135... timed out after 300s — still not 'stopped'` and `SoftTimeLimitExceeded()`. Checking Proxmox afterwards, the clone VMs (137, 138) *did* exist and finished — so they became orphans (real VM on Proxmox, `failed` in our DB, never started).
- **Root cause**: The clone-wait and Celery time limits were tuned for slim Linux golden images. A **full clone of a large Windows disk** runs several minutes; `clone_template_for_student`/`deploy_template_for_user` waited only `wait_for_task(timeout=300)`, and Celery's `task_soft_time_limit=720`/`task_time_limit=900` killed the still-healthy task. The Proxmox clone kept running to completion after our task bailed → orphan VMs. Compounded by `_SOURCE_LOCK_WAIT_SECONDS=600`: the 2nd same-source clone couldn't get the per-source lock in time and proceeded unlocked.
- **Fix** (`backend/app/tasks/clone_tasks.py`, `backend/app/celery_app.py`):
  - Added `_clone_wait_timeout(os_choice)` → 1500s for `windows-11`, 600s otherwise; used in the student-clone and deploy tasks. `build_template` clone wait bumped to 1500s.
  - `_SOURCE_LOCK_WAIT_SECONDS` 600→3600, `_SOURCE_LOCK_HOLD_SECONDS` 600→1800 (enough for several back-to-back Windows clones serialised on the same source).
  - Celery `task_time_limit` 900→3600, `task_soft_time_limit` 720→3300.
  - Requires a **celery-worker restart** (worker doesn't hot-reload task code or Celery config).
- **Orphan cleanup**: VMs left by a timed-out clone exist on Proxmox but are `failed` in vm_jobs — delete them on Proxmox (or via the app) to reclaim storage; no auto-cleanup yet.
- **Lesson**: A clone-wait timeout must be sized for the *worst* OS/disk you actually clone, not the fast path — and it must sit *below* the Celery hard limit, or the orchestrator kills a healthy job mid-flight. Also: "our task gave up" ≠ "the work stopped" — Proxmox finishes the clone regardless, so a too-short timeout silently produces orphans, not clean failures. For large Windows images, **linked clones off the real template** (now possible since publish makes a true Proxmox template) are dramatically faster/smaller than full clones. See [[11-clone-templates]].

## Issue 14: Publishing templates from deleted Proxmox VMs (Stale VMs)
- **Symptom**: In the "Publish Template" modal, admins saw VMs that they had previously deleted directly inside the Proxmox UI. Selecting one to publish caused downstream failures because the VMID no longer existed on the hypervisor.
- **Root cause**: The `GET /admin/vms` endpoint only returned records from the local `vm_jobs` database table. It never verified if the VMs actually existed on Proxmox, leading to UI staleness if an admin managed VMs out-of-band.
- **Fix**: Added an optional `verify_proxmox` query parameter to the `GET /admin/vms` backend endpoint. When `true`, it cross-references the DB results with `proxmox_client.list_vms()` and strips out any `vmid` not found on the host. Updated the React UI `PublishModal` to fetch verified VMs.
- **Lesson**: The local database is a cache of intent; the hypervisor is the source of truth. Features that rely on VM existence (like publishing a template) must verify state with the hypervisor to prevent operations on phantom records. Note: This implementation only filters the read API and does not proactively delete DB records.

## Issue 16: Stale VMs properly reconciled via write-back (supersedes the read-only filter of Issue 14)
- **Symptom**: Same class of bug as Issue 14 — VMs deleted directly in the Proxmox UI kept showing in the app ("hallucinated VMs"). The earlier mitigation (a `verify_proxmox` flag that *filters* the `GET /admin/vms` response against live Proxmox) only cleaned up one endpoint's response and never wrote anything back, so the DB stayed permanently stale and the user dashboard / every other read path still hallucinated. A separate attempt had pulled live Proxmox data straight into the UI, which made the UI depend on Proxmox being reachable for *correctness* (not just telemetry).
- **Root cause**: `vm_jobs` is a cache of intent; Proxmox is the source of truth for existence. Nothing was reconciling the two — the DB never learned that a VM had been removed out-of-band.
- **Fix**: Reconcile-on-read with **write-back**. New `backend/app/services/reconciliation.py` → `reconcile_vm_existence(jobs, live_vmids)`: for any job in `status in {running, done}` whose `vmid` is absent from the live Proxmox VMID set, it calls the new `db/database.py:mark_vm_job_deleted(job_id, reason)` to soft-delete the row (`status='deleted'`, preserving `proxmox_response`, appending a reason to `error_message`) and writes a `vm.reconcile_deleted` audit row. Wired into `vm_routes.list_user_vms` (reusing the existing single bulk `list_vms()` call) and `admin_routes.list_all_vms` (replaced the filter-only `verify_proxmox` path). Because `list_user_vm_jobs` already filters `status != 'deleted'`, reconciled VMs vanish from the dashboard with **no frontend change**.
- **Two guards (critical)**: **G1** — only reconcile when the live `list_vms()` call *succeeded* (a `proxmox_reachable` flag / the `try` that builds `live_vmids`), so a transient Proxmox outage can't mass-delete the inventory. **G2** — only `running`/`done` rows are eligible; never touch `queued`/provisioning rows, whose reserved VMID isn't on Proxmox yet (`get_reserved_vmids` depends on this).
- **Key design insight**: The DB `vm_jobs.status` column is the *provisioning lifecycle* (`queued→running→done→failed→deleted`), **not** the power state. Reconcile *existence*; leave power state / CPU / memory / uptime as live enrichment — those are real-time telemetry, not stale cache.
- **Lesson**: "Filter the response" hides the symptom on one endpoint; "write the truth back to the DB" fixes the class of bug everywhere and lets the UI go back to reading the (now self-correcting) DB. When the local store is a cache of a remote source of truth, reconcile *into* the store rather than papering over reads. And always guard a reconciliation pass against the upstream being unreachable. See [[12-state-reconciliation]].
